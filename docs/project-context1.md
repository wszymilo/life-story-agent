# Idea behind the project
## Life Story Preservation Agent

### Overview

A conversational AI system designed to support elderly individuals to gather information about their life stories, capturing memories through empathetic dialogue, organizing collected narratives into coherent chapters, and producing shareable family legacy documents. The system acts as a patient, curious, and respectful oral historian who treats every life as worthy of documentation. The system support the user in the process of creation of stories by gathering the story itself plus some supplemental information about the story, if the narrative part misses them.

Supplemental information may be (list is open-ended): 
    - time of the events, 
    - family context,
    - historical context remembered by the user
    - etc.
    
Single story or memory forms an event for the sake of further explanation.

|Dimension|Decision|
|---|---|
|Primary User|Your ~80-year-old mother|
|Access Device|Mobile phone (primary)|
|Architecture|JS frontend (mobile app) + Cloud backend|
|Development Approach|AI-assisted via OpenCode|
|Timeline|10 days|
|Team|Solo developer|

### Core Concept

Upon onboarding within the system the user define:
 - their birth date,
 - their name,
 - their relatives (Elders of theirs, siblings, kids, grandkids, etc.).
 - their country of origin
 - System stores the information and prepares an empty life line, ready to fill in with stories & memories.

A) If the user wants to register a memory/story/event:
 - the agent invites them to talk about it; system records their voice and create transcription.
   - then the system analyze the transcript to:
     - make sure it contains any information about the time of the event (even rough, like 'it was during the spring of 1956'). 
       - if missing, the system asks targeted questions to embed the event on the time line.
     - make sure it contains any information about the place the event was happening
       - if missing, the system asks targeted questions to embed the event in space.
     - identify persons/names or important sub-events mentioned in the initial transcript that may be worth gathering attitional information about
   - having the event positioned on the time line, space and potential subjects to explore more, the system starts to ask gentle, openended, AI-generated, follow-up questions (preferably using TTS) to the recorded story, seeking a way to deepen the story, and at the same time allowing the user to restore/refresh their memory about the event. 
   - the user is able to record their responses, and the system transcribe these and add to the story.
   - the user is able to refuse answering any of the supplemental questions
     - system does not store rejected questions
   
 - at any time user can decide to end the session
   - In response, the system gathers all artifacts from the session:
     1) all audio parts,
     2) the answered follow-up questions in text form,
     3) the transcripts of all audio parts
     4) system find one interesting historical fact/happening that is close to the date of the event from each:
        - the world outside of the country of origin for the user
        - from the country of origin for the user
   - creates faithful and grounded in registered facts summary of the gathered informations and adds that to the artifacts.
   - The system offers an option to present the summary of the gathered information, ideally in a form of TTS rendered audio.

B) Upon end of the session the new event appears on the timeline, and the user can see the event. 
If the user taps on the event on the timeline the system offers:
 - the option to listen to the informations stored in the event
 - the option to remove the event (with confirmation to avoid accidental removals)
 
C) The user has an option to publish one, a selection of or all events in a form of narrative story grounded in the facts gathered for each event being published.
 - the system synthesize the narrative story based on the information archived in all events selected for the publishing
 - the system allows presentation of the narrative story, preferable as audio generated by TTS
 - the system allows downloading the story as zipped file containing:
   - markdown version of the synthesized narrative story
   - all audio and text sources that were used to build the story, separated into per-source-event-from-the-timeline-subdirectories

   
### Follow-Up Question Generation

When deepening a story, the system generates follow-up questions by:
- Pure LLM generation based on transcript analysis

The questions aim to:
- Elicit sensory details ("What did it smell like?")
- Explore emotions ("How did that make you feel?")
- Identify other people involved ("Who else was there?")
- Connect to broader context ("What else was happening in your life then?")

### What Constitutes an "Event"

An event is a single memory or story anchored to a point on the user's life timeline. 
One session may capture one event. Each event has:
- A time anchor (specific date, month/year, season/year, or life period)
- One or more audio recordings with transcriptions
- Follow-up Q&A exchanges
- A generated summary
- Status: draft (in progress) | complete (session ended)

### Contextual Enrichment

The system may enrich stories with contextual information:

**User-provided context** (always):
- Family members mentioned
- Places mentioned → stored for potential map integration (future)

**System-retrieved context** (stretch goal):
- Historical events contemporary to the story's timeframe
- Retrieved via querying Wikipedia for interesting facts from the timeframe for both:
  - world-wide scenery
  - country-specific scenery
  

### What is a "Session"

Session refers to the process (initiated by the User) that serves the purpose of collecion of all artifacts constituting a Story/Event on the User's life time. The artifacts may be (list is open-ended):
 - all audio parts,
 - the answered follow-up questions in text form,
 - the transcripts of all audio parts

### What is "Publishing"
Publishing is the act of creation of narrative, grounded in gathered artifacts description of whole (or a part of) user's timeline expressed by the events registered on the timeline within the boundaries set by the user.

The output of the publishing stage is markdown file plus source artifacts that were foundation of the generated material, all zipped to one file.

# Technical Decisions

## LLM & AI Services
- Primary LLM: OpenAI gpt-5-nano
  - Rationale: Cost reduction during development
- Speech-to-Text: Whisper API (OpenAI)
  - Rationale: High accuracy, handles accents well
- Text-to-Speech: OpenAI TTS
  - Rationale: Natural sounding, simple API

## Backend
- Language: Python 3.12
- Framework: FastAPI
- Agent Framework: OpenAI Agents SDK + litellm for non-agentic LLM calls
- Primary DB: PostgreSQL (via Supabase)

## Frontend
- Framework: React 18
- Mobile Approach: PWA (Progressive Web App)
  - Rationale: No app store needed, works on any phone
- UI Library: Tailwind CSS + shadcn/ui
- Audio: Browser MediaRecorder API

## Deployment
- Backend: Railway (simple Python hosting)
- Frontend: Vercel (static + serverless)
- Database: Supabase (managed PostgreSQL)

## Security
- Simple auth: magic link via email (Supabase Auth)
- HTTPS: Automatic via hosting providers

## Observability / Evals
- Built-in logs
- Sentry for error tracking
- LangFuse for evals - perhaps with option to self-host on Railway

## Session State Management

What happens in edge cases?

- Auto-save audio immediately after each recording stops
- If User closes app mid-recording, audio is lost, we keep the draft state in Event model (status enum)
- Auto-save transcript after each transcription completes
- Session state (draft event + recordings) persists in Event model with proper status
- User can return to draft events and continue to complete them
- Pausing of the session is not supported

## Generator-Reviewer Pattern Specifics

Generator-Reviewer tandem is defined as a loop with separate LLM calls (generate → review → regenerate). Each call use structured output. 

Reviewer checks for:
   - Every claim in summary has source in transcript
   - No fabricated details
   - Tone is warm and respectful
   
(Re)Generator uses dynamic system prompts to generate (or regenerate) the summary. If Reviewer rejects a version of the summary it returns reasons and examples of bad generation. Generater reattempts generation havint the feedback added to the context. There is a limit of 2 rejections, if that limitation is reached we use the last attempt with a flag informing about that fact.
